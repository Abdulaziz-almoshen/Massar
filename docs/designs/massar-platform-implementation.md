## What the founder asked for

The full platform, not the CRM spine: *"Everything with the WhatsApp engine, with the campaign
configuration, with the responses, with the profiling."* Plus the product hub, where a product
manager uploads material the AI agent uses on a campaign, a rep opens the same product to learn it
before a call, files can be uploaded, and a sales deck is generated from that material and kept in
the CRM.

Five layers, then. Here is the honest state of each, measured against the source.

| Layer | Today | Gap |
|---|---|---|
| **WhatsApp engine** | `gupshup.ts` 290 lines, send + v1/v2/v3 webhooks. Live: 356 messages, 1,228 events, 21 contacts. | On a **sandbox** number. No send gate, no outbox, no idempotency, no per-template lifecycle. |
| **AI responses** | `agent.ts` 1,726 lines, 9 tools, opt-out and turn caps in code, knowledge scoped per product. | No shadow evaluation, no retrieval citations, no regression evals against approved content. |
| **Campaign configuration** | `templates.ts` holds Meta templates as hardcoded data; a 3-step wizard. | Templates are **code, not records**: no submission tracking, no per-template quality rating, no pacing state. |
| **Profiling** | `facts.ts`, 17 typed keys with provenance and a refusal ladder. | Coverage near zero: no import carries the HIS/ERP columns, so the agent still interviews everyone. |
| **CRM** | Opportunity board, client record, campaign monitor, tasks, notes. | No users, roles or departments. No handoff. One pipeline per account. Calls and visits have nowhere to live. |
| **Product hub** | `product_kb` + `product_assets`, both keyed on product name. | **One** knowledge document and **one** file per product. No versioning, no approval, no deck. |

## The finding that reorders everything

I went looking for the outbound safety layer and there is not one.

- **No global send gate.** Zero matches across 15,780 lines for a kill switch, dry-run flag, or any
  `canSend`-shaped guard. Nothing exists to deny by default.
- **No idempotency on the send path.** Nothing marks a message as already sent.
- **Opt-out is an application check in one place** (`index.ts:360`, inside a single route's loop),
  not a structural guard at the send boundary.
- **`campaign_targets` records no send.** It is `(campaign_id, phone, name)` and nothing else. No
  `sent_at`, no provider message id, no status. The primary key prevents a duplicate target row; it
  does nothing to prevent a duplicate **send**.

Today none of this can hurt anyone, because the founder's zero-send rule is the safety layer. That
rule is a human promise holding back a system that has no brakes of its own. The day production
credentials are introduced, every stale job, test fixture and retry becomes a real message to a real
clinic.

**EUREKA.** The research adds the sharp edge. Meta rates **each template** green, yellow or red, and
applies **pacing** to any template not yet Active-High: it will not let a new or degrading template
go out at volume. So number health is not one number. A single bad template can throttle a campaign
while the account's aggregate rating still looks fine, and nothing in Massar can see that, because
templates are constants in a source file rather than records with a lifecycle.

`CLAUDE.md` names protecting the WhatsApp number as goal 4 and says never burn it. The platform
currently protects it with a promise. **That is what to build first, and it is not where the
47-week plan started.**

## Premises (auto-agreed, recorded)

1. The commercial semantics are the missing thing, not the infrastructure. A second application does
   not add a handoff, a product track, or an engagement.
2. The outbound path needs structural brakes before it needs features. Deny by default, an immutable
   outbox, idempotency, a suppression ledger, a circuit breaker.
3. Template quality is per-template and paced by Meta. Templates must become records with a
   lifecycle, not constants.
4. Profiling already exists and is empty. The fix is upstream (imports and enrichment), not a new
   model.
5. Product knowledge must be versioned and approved, and must separate what the **agent may say**
   from what a **rep may read**. They are different audiences with different risk.
6. Every generated artefact — a deck, a suggestion, a fact — carries its source or it does not ship.

## Architecture

Everything below lands **inside `massar-engine`**. No second application, no parallel run, no
cutover.

### The outbound safety layer (new, phase 0)
```
send_gate          global deny-by-default; SEND_ENABLED must be explicitly on,
                   plus a per-environment allowlist of destination numbers
outbox             (id, kind, to_phone, template_id NULL, payload, idempotency_key UNIQUE,
                    state ∈ queued|sent|failed|suppressed, provider_msg_id, attempts,
                    created_at, sent_at, error)
suppressions       (phone PRIMARY KEY, reason ∈ opted_out|invalid|bounced|manual,
                    created_at, created_by)     -- consulted INSIDE the gate, not by callers
send_audit         append-only: who, what, when, which gate decision, which template version
circuit_breaker    per-template and per-number: trips on failure rate or quality drop
```
Every path that reaches WhatsApp goes through the gate. The gate consults suppressions itself, so a
new caller cannot forget. `idempotency_key` makes a re-run structurally incapable of a second send.

### Identity and the commercial spine (phase 1)
```
users              (id, name, email, password_hash, department_id, role, active)
departments        (id, name, kind ∈ product|sales|other)
sessions           (token, user_id, issued_at, expires_at, revoked_at)
accounts           (id, name, name_normalized, city, size, sector, parent_account_id,
                    attrs, facts, created_by, merged_into_id)
account_contacts   (id, account_id, name, role_title, phone_e164, email, is_primary)
                    UNIQUE (account_id, phone_e164)
phone_routing      (phone_e164 PK, account_contact_id)   -- the one inbound route
handoffs           (id, from_user_id, from_department_id, to_department_id, to_user_id,
                    product_id, title, note, method, sla_days DEFAULT 14, created_at)
handoff_items      (id, handoff_id, account_id, track_id, assigned_user_id, status)
product_tracks     (id, account_id, product_id, pipeline_id, stage_id, owner_user_id,
                    source, source_handoff_id, sale_price, years, qty, discount,
                    opened_at, stage_at, closed_at, close_reason)
                    UNIQUE (account_id, product_id) WHERE closed_at IS NULL
engagements        (id, account_id, track_id, contact_id, actor_user_id,
                    channel ∈ call|visit|whatsapp|campaign|email|other,
                    direction, occurred_at, outcome_id, note_text, form JSONB,
                    form_schema_id, voice_asset_id, source ∈ manual|agent|webhook)
                    APPEND-ONLY. Corrections are new rows, never edits.
```

### Product hub, versioned (phase 3)
```
products           (id, name, department_id, active)
product_versions   (id, product_id, version, state ∈ draft|in_review|approved|retired,
                    approved_by, approved_at, expires_at)
product_sources    (id, product_version_id, filename, mime, bytes_ref, uploaded_by,
                    kind ∈ brochure|faq|pricing|technical|case_study)
product_claims     (id, product_version_id, claim, source_id, page_ref,
                    audience ∈ agent|sales|both)   -- agent may only say audience ∈ agent|both
product_assets     (id, product_version_id, filename, sendable BOOLEAN)
```
`product_claims` is the join that makes the whole hub honest: every sentence the agent may say, and
every line a rep reads, points at the file and page it came from. The **audience** column is what
separates what the agent may state from what a rep may know.

### WhatsApp control plane (phase 5)
```
templates          (id, name, category, language, body, buttons JSONB,
                    meta_template_id, state ∈ draft|submitted|approved|rejected|paused,
                    quality ∈ unknown|green|yellow|red, paced BOOLEAN,
                    submitted_at, approved_at, rejection_reason, version)
template_events    append-only: every state and quality change Meta reports
```
This is what turns `templates.ts` from constants into a managed asset, and it is what lets the
circuit breaker act on a single degrading template instead of the whole number.

## Plan

| Phase | What ships | Proof it is done | Weeks |
|---|---|---|---|
| **0** | **Outbound safety.** Global deny-by-default gate, immutable outbox with idempotency, suppression ledger consulted inside the gate, send audit, per-template and per-number circuit breaker, environment-separated credentials. **Sending stays disabled.** | A replay of every historical campaign through the gate sends nothing and logs a decision per attempt; a deliberate double-run of one campaign produces one outbox row, not two | 3 |
| **1** | Identity and the commercial spine: users, departments, roles, sessions, accounts, contacts, phone routing, handoffs, product tracks, append-only engagements | Four real people log in; a PM hands 50 accounts and names every one untouched; one clinic runs two tracks at two stages with two owners | 6 |
| **2** | The existing dashboard moves onto the model: CRM records, product tracks, the rep's day, calls and visits, pipeline views, handoff queues, the PM outcome dashboard | Every screen in the live product reads the new model; a rep logs a call in under 10s and is handed a drafted follow-up | 4 |
| **3** | Versioned product hub: multi-file upload, extraction to claims with page references, approval workflow, expiry, agent-usable versus sales-readable split, the rep's product page | A product manager approves a version and the agent's answers change on the next message; a rep reads the objection sheet before a call | 3 |
| **4** | Agent quality: shadow mode against approved snapshots, retrieval with citations, regression evals, per-tool authorization, claim restriction to the approved version | Every agent sentence in an eval transcript traces to an approved claim; a retired version stops being quotable within one message | 3 |
| **5** | WhatsApp control plane: production WABA readiness, template records, submission and versioning, per-template quality and pacing state, approval-gated campaigns, rate limits, retries, breakers | A template's quality change from Meta lands as an event and pauses only that template; the campaign wizard refuses a paced template | 4 |
| **6** | Profiling filled: enrichment at import, HIS/ERP vendor registry, fact coverage on the record, agent stops asking what is already known | Fact coverage rises from near zero to a stated number on real accounts; the agent asks a question it previously asked and is refused | 2 |
| **7** | Sales decks generated from approved claims, with the critic, human review mandatory before publish | A deck cites every slide; a slide with no approved claim renders blank rather than invented | 2 |
| **8** | Progressive send enablement — **only if the founder lifts the zero-send rule.** Two or three templates, ~20 opted-in recipients, measured | Delivery, replies, opt-outs and per-template quality observed on a real pilot | 2 |

**29 weeks of work (3+6+4+3+3+4+2+2+2). With a 15% buffer, plan on 33 weeks.**

That is **14 weeks less than the 47-week rebuild, and it delivers more**: the rebuild's 47 weeks did
not include the WhatsApp control plane, the versioned product hub, agent evaluation, profiling
enrichment, or decks. The saving comes almost entirely from not building a second application and
not running a 22-week parallel period. (The column is summed, not estimated — two earlier drafts in
this project quoted a total that did not match their own phase table.)

## What this deliberately does not build

- A second application, a dual-write period, or a cutover.
- A generic workflow engine or a visual pipeline builder.
- A dashboard builder.
- Autonomous deck publishing — a human approves every deck.
- Autonomous outbound sending — the gate stays deny-by-default and a human approves every campaign.
- A campaign scheduler beyond the minimum, until a real pilot has been observed (A10).

## Risks

| Risk | Mitigation |
|---|---|
| Production credentials turn stale jobs into real sends | Phase 0 ships before anything else; the gate denies by default and every path routes through it |
| One template degrades while the number looks healthy | Per-template quality and pacing state, with a breaker that pauses one template |
| A re-run sends twice | `idempotency_key` UNIQUE on the outbox — structural, not a code path |
| Opt-out regresses | Suppressions are consulted inside the gate, so a new caller cannot forget |
| The agent quotes retired material | Claims are versioned; a retired version stops being quotable, proven by eval |
| Extending v1 destabilises a working product | Every phase behind the existing 16-step gate and the Playwright smoke test; `dashboard.ts` edits stay anchored under ADR-0001 |
| Profiling stays empty | Phase 6 is enrichment at import, not a new model; coverage is stated as a number |
