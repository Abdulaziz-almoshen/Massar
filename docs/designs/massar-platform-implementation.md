## What the founder asked for

The full platform: *"Everything with the WhatsApp engine, with the campaign configuration, with
the responses, with the profiling."* Plus the product hub, where a product manager uploads
material the AI agent uses, a rep opens the same product to learn it before a call, files can be
uploaded, and a sales deck is generated from that material with a critic.

**That scope is unchanged in this document.** The review did not cut it. It corrected what the
document said about the code, fixed defects that made it unexecutable, and added the prerequisites
the first estimate omitted.

## Five defects that exist in production today

Found while checking the plan's claims. None is caused by this plan; all are made worse by it.

1. **An inbound «إيقاف» can be lost.** `index.ts:41` acks the webhook *before* persisting
   anything. A process death after the ack loses the event permanently and the number stays
   sendable. No suppression ledger fixes this, because the loss precedes any write.
2. **A provider timeout sends the message twice.** `gupshup.ts:44` is a bare `fetch` with no
   `AbortSignal` (there is none anywhere in the codebase), and `agent.ts:1503-1509` catches a
   failed quick-reply and re-sends the same content as plain text. If Gupshup accepted the first
   one, the customer gets both.
3. **A failed migration reports healthy.** `db.ts:321` catches it and starts in memory-only mode;
   `/health` returns `ok: true` unconditionally.
4. **The webhook accepts forged POSTs when the token is unset.** `if (cfg.webhookToken && ...)` —
   an empty token makes the guard false. `configReport()` prints "webhook is unauthenticated!"
   and the app boots anyway.
5. **Per-recipient launch failures are computed, returned, and dropped.** `index.ts:428` returns
   `failed: [...]`; nothing in `dashboard.ts` reads it. The UI shows only «أُرسلت N من M».

## The finding that still reorders everything

Not "there are no brakes" — there are, in four places, and almost nothing uses them.

**A door standing in a field is worse than no door**, because its existence reads as coverage.
`outbound.ts` makes, in its own header, the exact promise this plan made for its new gate: *"This
module holds the POLICY so it cannot be re-derived per call site."* Within one cycle the
highest-traffic caller went around it, and the guard script has been announcing that on every
build since.

**A second policy module will hold no better than the first.** The seam has to be structural: the
gate becomes the only module that can name `gupshup.send*`, and a build check fails on any other
import. That is the difference between a convention and a mechanism, and it is the single most
valuable change in this document.

**And per-template pacing still matters.** Meta rates and paces each template individually, so a
degrading template throttles a campaign while the account looks healthy. But the pacing rule cuts
both ways: a template can only *leave* pacing by sending, so "the wizard refuses a paced template"
would mean no new template ever reaches Active-High. Pacing means a controlled low-volume state,
never blanket refusal.

## Architecture

Everything lands **inside `massar-engine`**. No second application.

### Phase 0a — foundations (nothing above is safe without these)
```
schema_migrations   numbered files, a version table, an advisory lock, run as a Fly
                    release_command so a bad migration FAILS THE DEPLOY instead of
                    half-booting into memory-only mode.  Today: one 230-line SQL
                    string run at startup AND by a 30s reconnect timer.
pg_dump             in the release command. There is no backup anywhere in the repo.
Testcontainers      a Postgres harness. The outbox's whole value is a concurrency
                    property and no pure-function test can observe one.
coverage.include    becomes a glob over src/*-domain.ts plus the safety modules.
                    Two lines. Today a NEW tested domain module stays outside the gate.
CI                  a GitHub Action running npm run check on push. There is none in
                    either repo, and npm run check gates only npm run deploy.
SIGTERM handler     there is none. A deploy mid-send strands rows with unknown outcomes.
AbortSignal         fetch timeout of 15s in gupshup.ts. A timeout is classified
                    `unknown`, NEVER `failed` — a timed-out send usually succeeded.
/health             returns ok:false when the database is enabled and not connected.
```

### Phase 0 — the one door
```
send-gate.ts        the ONLY module that may import the Gupshup send functions.
                    Enforced by check-onedoor.mjs in npm run check, built on the
                    technique in check-props.mjs (which already imports
                    dist/dashboard.js and evaluates the client bundle).
                    Exit criterion, stated as a number: bypassing call sites 13 -> 0.

  purpose           marketing | service_reply | consent_ack | internal_alert
                    consent_ack is EXEMPT from suppression — otherwise the gate
                    refuses the confirmation of the opt-out that just wrote the
                    suppression (agent.ts:1170 records, then sends).
                    internal_alert is exempt from customer-window logic.
                    The exemption set is asserted by a test.

  FAIL CLOSED       if the database is unreachable the gate REFUSES. Stated
                    explicitly because this codebase's prevailing idiom is the
                    opposite: fire() forgets writes when disconnected and
                    listOpps/listEntities return [] — a suppression lookup written
                    in the house style would read "no row" as "not suppressed".
                    This trades WhatsApp availability for consent integrity.

suppressions        (phone, reason, source, purpose_scope, consent_wording,
                     created_at, created_by, expires_at)
                    phone is BARE DIGITS, one normalizePhone (audience.ts, tested),
                    CHECK (phone ~ '^[0-9]{8,15}$'), and a boot assertion that
                    writer and reader agree. The first draft wrote `phone` in one
                    table and `phone_e164` in two others; a suppression written
                    +966... and read 966... answers "not suppressed".
                    BACKFILLED from contacts.opted_out as the FIRST migration, and
                    the gate reads BOTH sources until the backfill is proven equal.

outbox              (id, purpose, to_phone, template_id, payload, idempotency_key UNIQUE,
                     state, provider_msg_id, attempts, next_attempt_at,
                     claimed_at, lease_until, worker_id, created_at, sent_at, error)
                    state: queued | sending | sent | failed | suppressed | unknown | dead

  idempotency_key = sha256(template_id | template_version | to_phone
                           | rendered_body | window_bucket)
                    NOT the campaign id. createCampaign mints a fresh BIGSERIAL per
                    POST, so a key containing it never collides. Campaign creation
                    is itself made idempotent by a client Idempotency-Key stored
                    UNIQUE on campaigns.

dispatcher          CARVED OUT of A10's deferral. An outbox with no consumer is a
                    log, not a queue. Claims with FOR UPDATE SKIP LOCKED, holds a
                    lease, recovers after worker death, backs off with jitter,
                    dead-letters, and PRESERVES PER-PHONE ORDER — queue.ts
                    guarantees that today and a naive outbox would discard it.

inbound_events      (wa_message_id UNIQUE, raw, received_at, processed_at)
                    Persisted BEFORE the webhook acks. Today the route acks first
                    and a crash loses the event — including an «إيقاف».
                    The webhook refuses to boot without WEBHOOK_TOKEN, and the token
                    moves out of the query string.

send_audit          append-only: who, what, when, which gate decision, which
                    template version, correlation id.
                    AND IT HAS AN OPERATOR SURFACE. index.ts:428 already returns
                    per-recipient failures and dashboard.ts never reads them; a
                    decision log nobody can see repeats that.
```
The per-template circuit breaker moves to **phase 6**, where its input exists.

## Design, specified

The first draft named screens and specified none. It also never referenced the thirteen finished
artboards at `_مسار/v2/`, which answer most of its open questions.

**Design source.** The artboards are binding storyboards; **`DESIGN.md` wins wherever they
disagree**, and they disagree in three known ways (rounded bordered list wrappers where the system
requires flush rows, filled status chips where state is a dot plus label, extra tinted surfaces
beyond the single teal accent). They are also all fixed at 1440x900 with **zero media queries**,
so they are not mobile references.

```
  PHASE                 ARTBOARDS
  spine (2)             Handoff · Duplicates · SalesInbox
  surfaces (3)          Main · Account · Outcome
  product hub (4)       Products · ProductKnowledge · ProductForSales
  control plane (6)     Campaign · CampaignMonitor · Conversation
  decks (8)             PitchDeck
```

**Four roles, each with a landing screen and its first three elements.** The artboards show four
personas, not three, and the live product already disagrees with itself about home (default route
is `#kmon`, the nav's first item is «الرئيسية»).

```
  ROLE            LANDS ON     FIRST              SECOND             THIRD
  مندوب (mobile)  #today       what must I do now who has gone quiet what is new for me
  مدير المبيعات   #inbox       overdue / unowned  who is behind      pipeline by stage
  إدارة المنتج    #outcome     what happened to   what customers     which product moves
                               what I handed off  said, verbatim
  admin           #gate        gate decisions     template health    audit
```
**Navigation is filtered by role, never by table.** Without this rule a 25-item rail exposing the
schema becomes the default.

**Every state is specified, because on day one every screen is empty.**
DESIGN.md's honest-absence vocabulary («لم تُرسل بعد» · «بلا جمهور» · «—») gains two entries the
gate needs: «مُنع» (refused) and «أُوقف تلقائيًا» (breaker). Every empty state names why it is
empty, who can change that, and the one action that does. «لا توجد بيانات» is not a design.

**The rep's flow is phone-first**, because a rep logging a visit is standing in a clinic holding a
phone. Tested at 360/390/430 CSS px, one-handed, 44px targets, no horizontal table scrolling,
account context pinned, **outcome first and note second**, the engagement **saved before** the
follow-up is generated, drafts surviving interruption, and a visible difference between «حُفظ» and
«أُرسل» — a rep who believes a follow-up was sent when it was only saved will not chase it.

**The rep's drafted follow-up ships in phase 3, but its grounding (approved claims) arrives in
phase 4.** Until then it is labelled «مسودة — راجعها قبل الإرسال».

**Arabic rules, as acceptance criteria.**
- Arabic-Indic numerals for **quantities a person counts**. Latin, `dir="ltr"`, monospace and
  copy-on-click for **identifiers a machine assigned** — `provider_msg_id`, `meta_template_id`,
  `idempotency_key`, phone numbers, match scores. `check:numerals` gains an allowlist for that
  class. A Gupshup message id rendered ٤٥٦٧٨ cannot be pasted into a support ticket.
- Counted nouns are four-way. `pluralizeArabic` exists in `opps-domain.ts:183` and
  **`dashboard.ts` calls it zero times in 4,127 lines**. The retrofit is a line item in phase 3,
  and a check flags any number concatenated with an Arabic noun.
- Every enum value gets an Arabic singular, dual, plural and sentence form, keyed by
  **(column, value)** — never by value alone. `manual` means two unrelated things, `other` means
  three, and `product`/`sales` sit on two different axes. Asserted at boot, following the existing
  `PROP_KEYS`/`PROP_LABELS` pattern in `tracker.ts`.
- Mixed Latin inside Arabic is isolated with `<bdi>`. There are **zero** in the codebase today,
  and phase 4 is a file-upload screen whose primary content is mixed filenames.
- Dates pin the calendar explicitly and all SLA arithmetic anchors to `Asia/Riyadh`.
- One state dimension per list row. Where two are genuinely simultaneous, one combined token
  («معتمد · جودة متدنية»), never stacked chips.

**Accessibility is acceptance criteria, not aspiration:** keyboard traversal with visible focus,
logical focus order in RTL, focus trap and restore, screen-reader announcements on save, failure
and async extraction, status never encoded by colour alone, reduced motion, 200% reflow. The
artboards are built from styled `div`s and must not be used as implementation references for
controls.

## The stop rule

Both predecessor documents carried a kill criterion. The first draft of this one carried none,
across 33 weeks. **A 44-week programme needs one more than a short one does.**

**Gate A — adoption, at the end of phase 3a (about week 16).** The rep queue and the PM outcome
view ship first within phase 3 so the window closes before 3b and 3c are built. Measured per
rep-day, never per track: if, three weeks after one named rep has the queue, that rep records
**fewer than three engagements on a median working day**, or **fewer than half the calls they say
they made** appear within 24 hours, phases 4 through 8 do not ship as designed. The programme
returns to the tap-only record and the sheet.

**Gate B — the send pilot (phase 9).** Only if the zero-send rule lifts.

**Neither gate can be assessed without The Assignment**, which remains unclaimed: reconstruct the
last three handoffs by hand and bring back how many accounts were never touched, the median days
from handoff to first contact, and how many reached a real conversation. Half a day of work, and
it is the cheapest item in this document.

## Economics

The first draft had none. Delivery, reply and opt-out rates are channel telemetry, not a business
case: a campaign can perform well on all three and produce no revenue.

Before phase 2, state a target for: cost per qualified conversation (Gupshup + Meta + model +
storage), reps' time saved per week, follow-up latency reduced, and deals recovered from abandoned
handoffs. **Every phase from 3 onward carries one number a Lean sales manager would repeat
unprompted.** Phase 2 does not pass on four logins; it passes on four people still logging in in
week three.

## The incumbent

**The shared Google Sheet.** It is free, familiar, and already open on both teams' screens, and
the first draft did not mention it once. A plan that avoids dual-write in software while creating
dual-entry in the organisation has moved the problem.

**Decision: Massar writes back to the sheet.** Its earned signals — last contact, stage, next
action, silence — land in the columns the team already opens, from phase 3a. Adoption is won by
being where people already are before it is won by being better.

## The operating model

An AI agent holding commercial conversations needs a named human for: escalation and its response
time, out-of-hours conversations, pricing and contractual questions, an incorrect or sensitive
answer, template approval, product-content approval and expiry, complaints and opt-outs, and
incident response. The data model has owners; the organisation does not. **Named before phase 9,
and before any real send.**

## What this deliberately does not build

A second application. A dual-write period. A generic workflow engine or visual pipeline builder.
A dashboard builder. Autonomous deck publishing. Autonomous outbound sending. A campaign scheduler
beyond the dispatcher — **which is explicitly carved out of that deferral**, because an outbox
without a consumer is a log, not a safety mechanism.

## Risks

| Risk | Mitigation |
|---|---|
| **Real customer numbers and verbatim transcripts sit in two PUBLIC repositories** (CLAUDE.md:71, founder's explicit decision Aug 24) | Owner and decision point named before phase 9. Every phase increases the volume. Production expansion and public transcripts are not indefinitely compatible |
| A new caller bypasses the gate | `check-onedoor.mjs` fails the build. The convention already failed here; the mechanism is the fix |
| The gate fails open on a database blip | Fail-closed is stated, tested, and check-scripted |
| Historical opt-outs are not backfilled | Backfill is the first migration; the gate reads both sources until proven equal |
| A re-run sends twice | The key formula is written down and unit-tested; campaign creation is itself idempotent |
| A timeout re-sends | Timeouts classify as `unknown`, never `failed`; reconciliation from the delivery webhook |
| An operator's button title crashes every boot | Validate at write, refuse at runtime. Phase 6's first deliverable |

| The migration breaks the only database | Numbered migrations, advisory lock, release command, `pg_dump`, expand-backfill-contract |
| The agent quotes retired or injected material | Versioned claims, per-claim human approval, injection eval |
| Nobody uses it | Gate A, and the sheet write-back |

## The one open question

Every voice in the review — two CEO, two design, one DX, two engineering, and this document's own
author — reached the same structural conclusion, with **zero disagreement across 19 scored
dimensions**: the architecture is right, and a 44-week programme that produces its first external
evidence in month four is the wrong shape for a team that has shipped one feature in the last
fifteen days.

Two of them proposed the same alternative independently: **an eight-week wedge** — the one-door
gate, the handoff ledger, the rep queue with one-tap outcomes, the PM outcome view, and the sheet
write-back — measured against Gate A, and only then a decision about whether the remaining 30
weeks are the right 30 weeks.

**That is not auto-decided here.** The founder asked for the full platform in his own words and
reaffirmed it when challenged. This document therefore keeps the full scope and adds the gate, so
the wedge is the *first sixteen weeks of the same plan* rather than a different plan. If he wants
the shorter shape, stopping at Gate A is already the design.
